## 2. Promote-to-saas-pack lessons (the gold)

These five are the structural lessons that distinguish a real multi-tenant SaaS from a "single-tenant prototype with auth bolted on." Every saas-multi-tenant project starts with these baked in. Already promoted to factory rules — listed here for the saas-pack so future projects pull them as a unit:

1. **VIBE Rule 55 — every UX value lives in `user_preferences`, never hardcoded.** The first test user is just user #1 of N, not "the prototype." Magic numbers (`limit(50)`, `60*60*1000`, `min_score=4.5`) anywhere user-facing require a `user_preferences` column reference OR a written justification in the comment. [FACTORY-CHANGE-CANDIDATE: confirm rule auto-loads in factory `.claude/rules/vibe-standard.md` — it does as of v4.2.]

2. **VIBE Rule 56 — AI-Assisted Discovery over manual config forms (lessons.md #97).** "Paste 10 URLs" form-driven onboarding doesn't survive user #2 having different interests than user #1. The first interface for any "which X do I pick?" decision is a conversational AI agent that asks plain-language questions and proposes options with reasoning. Manual forms ship as power-user fallback only.

3. **Dispatcher-pattern cron — ONE pg_cron job per pipeline step, fans out per user.** Each tick queries `user_preferences` for users whose timezone × cadence × active_hours × active_days × last_run matches NOW, dispatches per-user HTTP POSTs via `pg_net.http_post` with `Authorization: Bearer ${vault.cron_secret}`. Never write one pg_cron job per user — doesn't scale past hundreds.

4. **Type-grouped fetcher gating (lessons.md #98).** Multi-tenant routes read the user's `sources` table, group by `type`, only invoke external API fetchers for source types the user has at least one row of. "Constant per-request API call count regardless of which user invoked" is a bug — it means user prefs aren't gating the work and shared API quota is burned for users who didn't ask.

5. **AI-at-the-Core (VIBE Rule 57, factory Rule 19, lessons #99-100).** Remove every AI call from the app: if ≥75% still works, AI is a bandage and the product is a competitor's lunch. ForgeMinds passes (~5% survives without AI). Architecture must admit AI failure modes: 4-layer no-hallucination pattern, prompt_version logging, model swap-ability via provider abstraction, substring-validation on LLM-paraphrased text. AI-as-marketing-copy with manual-form UI underneath is the most dangerous self-deception of 2026.

### 3.1 `user_preferences` canonical schema (PRESERVE VERBATIM)

```sql
alter table public.user_preferences
  add column if not exists timezone              text     not null default 'America/New_York',
  add column if not exists cadence_minutes       integer  not null default 30
    check (cadence_minutes in (15, 30, 60, 120, 240, 360, 720, 1440)),
  add column if not exists active_hours_start    integer  not null default 7
    check (active_hours_start between 0 and 23),
  add column if not exists active_hours_end      integer  not null default 23
    check (active_hours_end between 0 and 23),
  add column if not exists active_days           text[]   not null default '{mon,tue,wed,thu,fri}',
  add column if not exists recency_window_minutes integer not null default 120,
  add column if not exists score_lookback_minutes integer not null default 240,
  add column if not exists min_composite_score   numeric(4,3) not null default 0.45,
  add column if not exists max_articles_per_brief integer not null default 15,
  add column if not exists max_per_category      integer  not null default 3,
  add column if not exists max_per_entity        integer  not null default 2,
  add column if not exists last_run_at_by_step   jsonb    not null default '{}'::jsonb;
alter table public.user_preferences
  add constraint user_preferences_active_days_check
  check (active_days <@ array['mon','tue','wed','thu','fri','sat','sun']);
```

Pattern: every UX-affecting knob is a column with a CHECK constraint defining its allowed values, a `not null default` covering the previously-hardcoded literal, and a `comment on column` line documenting what the dispatcher / route reads it for. **Saas projects: rename `last_run_at_by_step` keys to your own pipeline step names; everything else is universal.**

### 3.2 pg_cron dispatcher SQL (the migration template)

```sql
create or replace function private.dispatch_forgeminds_cron(step text)
returns table (user_id uuid, request_id bigint)
language plpgsql
security definer
set search_path = public, vault, net
as $$
declare
  rec record;
  dow_token text;
  hour_now int;
  last_run timestamptz;
begin
  for rec in
    select up.user_id, up.timezone, up.cadence_minutes,
           up.active_hours_start, up.active_hours_end, up.active_days,
           up.last_run_at_by_step
    from public.user_preferences up
  loop
    dow_token := lower(to_char(now() at time zone rec.timezone, 'dy'));
    hour_now  := extract(hour from (now() at time zone rec.timezone))::int;
    if not (dow_token = any(rec.active_days)) then continue; end if;
    if hour_now < rec.active_hours_start or hour_now > rec.active_hours_end then continue; end if;
    last_run := (rec.last_run_at_by_step ->> step)::timestamptz;
    if last_run is not null and now() - last_run < (rec.cadence_minutes::text || ' minutes')::interval then continue; end if;
    -- Fire per-user HTTP POST via pg_net
    return query select rec.user_id, request_id from net.http_post(
      url := app_config_url() || '/api/cron/' || step,
      headers := jsonb_build_object('Authorization', 'Bearer ' || vault.decrypted_secrets_for('cron_secret')),
      body := jsonb_build_object('user_id', rec.user_id)
    );
  end loop;
end$$;

-- One cron job per pipeline step, ticking every minute.
select cron.schedule('forgeminds_ingest_dispatch', '* * * * *',
  $$select private.dispatch_forgeminds_cron('ingest');$$);
-- + score, curate, enrich, generate, deliver
```

### 3.3 Per-user route invocation pattern

Routes accept two invocation modes:

```ts
// src/app/api/cron/<step>/route.ts pattern
export async function POST(req: NextRequest) {
  const auth = req.headers.get("Authorization");
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) return new Response(null, { status: 401 });

  const body = await req.json().catch(() => ({}));
  const url = new URL(req.url);
  // Single user via query OR body
  const userId = url.searchParams.get("user_id") ?? body.user_id;
  // Batch via body array
  const userIds: string[] = userId ? [userId] : (Array.isArray(body.user_ids) ? body.user_ids : []);
  if (userIds.length === 0) return Response.json({ note: "no users specified" });

  for (const uid of userIds) {
    const prefs = await loadPrefs(supabase, uid);  // src/lib/pipeline/user-prefs.ts
    // ... per-user work, gated entirely by prefs
  }
}
```

### 3.5 Conversational onboarding agent prompt structure

System prompt has TWO blocks: a static one and a cacheable one. The cacheable block holds the RAG-retrieved catalog candidates (~50K tokens). Anthropic prompt-caching amortizes the cost across the conversation.

```ts
// src/lib/ai/providers/claude.ts
const systemBlocks: SystemBlock[] = [];
if (request.systemPrompt) systemBlocks.push({ type: "text", text: request.systemPrompt });
if (request.cacheableSystemPrompt) systemBlocks.push({
  type: "text",
  text: request.cacheableSystemPrompt,
  cache_control: { type: "ephemeral" },  // ← the cache marker
});
```

The agent's job (per `src/lib/onboarding/agent.ts`): pick 8-12 sources from the candidates, write one-sentence `reason` per source tying it to user intent. Validator pass: numeric/temporal/award claims must be substring-matchable against `candidate.description + " " + candidate.name`. Ungrounded claims → drop the pick.

`match_source_catalog` RPC pattern: SECURITY INVOKER (not DEFINER), `set search_path = public, pg_temp`, vector cosine ANN search filtered by paywall_tier IN allowed_tiers + geography && allowed_geographies. **The INVOKER choice is critical** — DEFINER trips the Supabase advisor with "Signed-In Users Can Execute SECURITY DEFINER Function" warnings. ## 4. Domain anti-patterns

What multi-tenant SaaS projects MUST NOT do (from real ForgeMinds bugs caught and fixed):

1. **Hardcoded cron schedules in code or `0,30 11-23 * * 1-5` literal in migration** — see VIBE Rule 55. Every cron timing knob lives in `user_preferences`.

2. **One pg_cron job per user** — doesn't scale past hundreds. Use the dispatcher pattern (§3.2): ONE job per step, ticks every minute, fans out via `user_preferences` lookup.

3. **Form-based onboarding with esoteric inputs** ("paste your 10 RSS URLs", "enter your API key for service X", "pick from this 200-item dropdown") — most users don't know which URLs/keys/items to pick. The first interface is a conversational agent that asks plain-language questions and proposes options. See VIBE Rule 56 + lessons #97.

4. **Fetcher loops that run for every user regardless of preferences** — e.g. `for (const user of users) { fetchFinnhub(); fetchBenzinga(); ... }`. Constant per-request API call count = bug. See §3.4 + lessons #98.

5. **Magic numbers** without `user_preferences` reference: `limit(50)`, `60*60*1000`, `min_score=4.5`, `setTimeout(..., 5000)`. Every magic number is either a `user_preferences` knob OR justified in a comment.

6. **Single-tenant data flow** that "we'll multi-tenant-ify later" — by the time you multi-tenant-ify, ~30+ call sites need surgery. Multi-tenant from day 1 OR document the explicit single-tenant boundary in DECISIONS.md.

7. **SECURITY DEFINER on RPCs that don't need elevated privileges** — trips the Supabase advisor with "Signed-In Users Can Execute SECURITY DEFINER Function." Default to SECURITY INVOKER; DEFINER only when the function genuinely needs to bypass RLS (e.g. `track_event` writing to `behavioral_events`).

8. **AI in deterministic paths** (factory Rule 20). Retry policy driven by AI examining a 503 status flakes; AI in routing decisions flakes. AI for classification/drafting/summarization/extraction from unstructured text only.

## 6. Compliance + disclosures

### 6.1 TOS-at-signup consent (v5.0 model)

Every multi-tenant SaaS needs:
- **TOS + Privacy Policy versions stored per user** (`profiles.tos_version_accepted`, `profiles.privacy_version_accepted`, `accepted_at`)
- **Explicit "I accept" checkbox** in signup flow — not "by signing up you agree" buried in fine print
- **Re-prompt on TOS change** — if `current_tos_version > user.tos_version_accepted`, gate the dashboard until they re-accept

### 6.2 Billing transparency (per-tier feature gates)

- **Tier displayed prominently** in dashboard header (Explorer / Builder / Architect / Architect+)
- **Per-feature LOCKED state** with cost CTA ("Unlock with Builder — $14.99/mo") instead of hiding features
- **No paid-source surprise** — onboarding agent shows `paywall_cost_usd_monthly` next to every paid recommendation BEFORE the user picks it

### 6.3 Data export + deletion (GDPR 15/17, CCPA 1798.105)

- **Account deletion** in Settings → Danger Zone, types "DELETE" to confirm, cascade-deletes via Postgres FKs (already wired in Phase 0 schema)
- **Data export** as JSON ZIP — every user-owned table's rows for `auth.uid() = user_id`. Phase 10 work; pattern: nightly Edge Function `export_user_data` writes to Supabase Storage signed URL valid 24h

### 6.4 Plan-tier feature gating language

- LOCKED message format: *"🔒 [Feature]. Unlocks with [Tier] ($X/mo). [What this feature does for you.]"*
- NEVER fake-render the feature with grey-out + "Upgrade" overlay — wasteful pixels. LOCKED state shows what the feature IS, what unlocks it, and a CTA.

## 8. Hostile Architect — saas-multi-tenant additions

Stress-tests every multi-tenant project should answer BEFORE V1:

1. **What happens when user #1000 onboards and the dispatcher queries become slow?**
   ForgeMinds answer: dispatcher does ONE indexed SELECT against `user_preferences` per minute. At 10K users with cadence=30, ~333 users match per minute. Index on `cadence_minutes` keeps the scan fast. Test the breakpoint with `pgbench` against `dispatch_forgeminds_cron('ingest')` to find when latency exceeds the 1-min tick window.

2. **What if a user's API key expires mid-cycle?**
   Currently: external fetch fails, route logs error, brief generation continues without that source. User gets a partial brief.
   v5.0 addition: per-user `source_health` cron checks API key validity weekly + flags expired keys + shows in-app banner "Re-authenticate Source X."

3. **What if Stripe webhook is missed (subscription state drifts)?**
   v5.0 needs: nightly Stripe reconciliation cron that pulls all customer subscriptions, compares to `profiles.tier`, fixes drift. Plus webhook signature verification + idempotency key per event.

4. **What if a user pauses telemetry and the aggregator already pulled their signals?**
   v5.0 needs: `user_preferences.community_brain_opt_in` flag. Aggregator filters by this flag every nightly rebuild. Opt-out is retroactive — community_aggregates rebuilds nightly anyway, so opting out has same-day effect.

5. **Cross-tenant data leak audit (every quarter):**
   - Sample 10 random users, query their `briefs.user_id` set, confirm 100% match the sampled user_id
   - Query `behavioral_events` for `user_id <> auth.uid()` as authenticated test users — expect 0 rows
   - Query `community_behavioral_aggregates` for any column resembling user_id — expect 0
   - Run Supabase Advisor → Security tab; expect 0 new findings since last audit

6. **What if a user signs up, types intent, gets proposals, then logs out without finalizing?**
   ForgeMinds answer: `source_suggestions` rows persist with `state='pending'`. Next login → onboarding agent resumes from `/onboarding/refine` showing those pending suggestions. v5.0: add 30-day TTL via partial index; pending suggestions older than 30 days get auto-archived.

7. **What if the onboarding agent suggests a paid source the user can't afford?**
   ForgeMinds answer: agent only proposes from candidates filtered by `allowed_tiers` (read from `user_preferences.paywall_pref`). Free-tier users never see paid options.

8. **What if pg_net.http_post fails (network blip)?**
   ForgeMinds answer: dispatcher logs the request_id; failed fires retry on next tick because `last_run_at_by_step` wasn't updated. Idempotent by design.

## 9. Intake questions for a saas-multi-tenant client

When VictorForge takes a saas-multi-tenant consulting engagement (or v5.0 onboards a new commercial customer), ask these BEFORE the kick-off proposal:

1. **How many tenants at V1, 6mo, 12mo?** Drives cron architecture (dispatcher pattern needed at 100+ users), Supabase tier (Pro mandatory at any prod traffic), Vercel tier.
2. **Free tier? Pricing tiers? Number of tiers?** Drives feature gating UI + Stripe products + per-tier `user_preferences` defaults.
3. **Bring-your-own-key vs use-ours?** Drives Vault integration + per-user-API-key UI + cost-attribution architecture. (Most consumer products = ours. Most B2B = BYOK option.)
4. **Delivery channels at V1?** File download / email / Slack / webhook / dashboard / SMS / push. Drives `user_preferences.delivery_channels[]` + per-channel handler implementation.
5. **Compliance jurisdictions?** US-only / EU (GDPR) / CA (PIPEDA) / multiple. Drives data-residency requirements, deletion SLAs, TOS/PP versioning.
6. **Vertical specialization?** Finance / health / education / B2B SaaS / other. Drives action template library + source catalog seed set + AI prompt vocabulary.
7. **AI cost ceiling per active user per month?** Drives model choice (Haiku vs Sonnet defaults) + caching strategy + provider mix.
8. **Self-host option?** Drives ForgeDesk-style local variant + Tauri + Ollama integration vs pure-cloud.
